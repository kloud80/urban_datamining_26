발상의 전환 — 무엇이 필요한지를 모델에게 먼저 물어본다.

정답 대신 도구 목록을 준다

LangChain · 2022

도구를 설명하고, 어떤 값을 넘겨야 하는지까지 알려 준다. 그래야 고를 수 있다.

모델을 두 번 부른다

1차 답변은 사용자에게 보여 주지 않는다

그래서 느리다. 딸깍 소리가 나면서 기다리는 그 시간이 이것이다.

같은 질문, 도구만 붙였다

“얼마 전 경기 결과가 어떻게 됐지?”

모델이 똑똑해진 게 아니다. 도구가 붙었을 뿐이다.

코드로는 세 조각뿐이다

함수 · 툴 목록 · 프롬프트

순서가 바뀐 것이 핵심이다 — 예전엔 정답을 주고 답하라 했고, 이제는 도구를 고르고 답하라 한다.

본문이 아니라 별도 필드로 온다

Function Calling

답변 문장에서 골라내지 않아도 된다. 그래서 안정적으로 자동화된다.

한 바퀴 더

학습 데이터에
들어갔다

“이런 질문에는 답하기 전에 검색을 거쳐야 한다” 를 SFT·RLHF 데이터에 넣었다.

지금 GPT 에 물으면 딸깍 소리를 내며 검색을 갔다 오는데 — 모델이 스스로 판단한 것이다.
반대편의 문제

돌아오는 답의 형식이 제각각이다

서비스마다 다른 HTML · XML · 제각각의 JSON — 매번 파싱 코드를 새로 써야 했다.

규약을 맞추자

MCP — Model Context Protocol

“내가 정해진 형식으로 물을 테니, 너도 정해진 형식으로 답해 달라” — 그게 전부다.

“한양대역 주변 커피숍 매출 분석해 줘”

데이터 플랫폼을 MCP 서버로 붙인 사례

LLM 혼자서는 못 하는 일이다 — 외부 데이터를 조회할 수 있어야 한다.

여러분의 코드

직접 만든 분석 함수도 도구가 된다

코드 제너레이터

이것도 똑같은 에이전트다

핵심 엔진은 처음에 만들어진 그 LLM 그대로다. 달라진 건 쥐여 준 도구뿐이다.

잘 되는 것과 헤매는 것

차이는 하나 — 공개된 코드의 양

학습에 쓸 코드가 인터넷에 얼마나 있었나 — 그게 그대로 성능 차이가 된다.

이 수업이 마지막까지 남기는 한마디

내 방향성이 없으면
이 친구도 못 잡아낸다

도구가 아무리 좋아져도 무엇을 물을지는 사람이 정해야 한다.
이번 학기 내내 같은 맥락으로 이어 온 이유다 — 히스토리를 따라 이해하면 새 기술도 어렵지 않게 붙일 수 있다.
정리
  1. 에이전트 = 정답 대신 도구 목록을 주고, 무엇을 쓸지 모델이 고르게 한다.
  2. 모델을 두 번 이상 부른다 — 그래서 느리다.
  3. 부르는 쪽이 function calling, 답하는 쪽이 MCP 로 표준화됐다.
  4. 코드 제너레이터도 정확히 같은 구조다.
다음 — 이 에이전트에게 무엇까지 맡기고, 무엇으로 채점할 것인가.
